<Note>
**Phase 6** of the DealMarket Cameroon build roadmap. This defines the Postgres schema (Supabase) implementing the [System Architecture](/product/system-architecture) and the design implications from [User Personas](/product/user-personas). Visual entity-relationship diagrams are produced in Phase 7; this document is the field-level source of truth those diagrams are drawn from.

## 1. Conventions

- **Primary keys**: `uuid` everywhere (`gen_random_uuid()`), never auto-increment integers — avoids leaking record counts and simplifies future multi-region/multi-country sharding.
- **Timestamps**: every table has `created_at timestamptz not null default now()` and `updated_at timestamptz not null default now()` (maintained via trigger). Soft-delete via `deleted_at timestamptz` where records must be recoverable/auditable (promotions, products); hard delete elsewhere (e.g., ephemeral push tokens).
- **Tenancy column**: every retailer-scoped table carries `retailer_id uuid not null references retailers(id)` directly or via a non-nullable join, so RLS can be applied uniformly (NFR-SEC-008).
- **Money**: stored as `numeric(12,2)` in the smallest sensible currency unit for the locale, plus a `currency` column (`char(3)`, ISO 4217) — never assume XAF-only, per the expansion strategy (NFR-SCALE-005).
- **Enums**: implemented as Postgres `enum` types where the value set is small and stable (status fields); lookup tables where retailers/admins need to extend the set (categories).
- **Auth linkage**: `auth.users` (Supabase-managed) is the source of identity; `consumers` and `staff_members` are 1:1 profile extensions keyed on `auth_user_id`, never duplicating credentials.

## 8. Row-Level Security Approach

RLS is enabled on every tenant-scoped table (NFR-SEC-008). Policies follow three repeatable patterns rather than one-off logic per table:

| Pattern | Applies to | Rule |
|---|---|---|
| **Tenant-owned** | `promotions`, `flyers`, `sponsorships`, `subscriptions`, `payments`, `marketing_content_drafts`, `campaign_recommendations` | `retailer_id = (select retailer_id from staff_members where auth_user_id = auth.uid())`, further narrowed by `branch_scope` for branch-limited roles (Brice persona) on `promotions`/`flyers`. |
| **Consumer-owned** | `favorites`, `wishlist_items`, `shopping_lists`, `store_follows`, `notification_preferences` | `consumer_id = (select id from consumers where auth_user_id = auth.uid())`. |
| **Public-read** | `products`, `categories`, `promotions` where `status = 'published'`, `branches` | Readable by any authenticated or anonymous client (FR-AUTH-002); writes always go through Edge Functions, never direct client writes. |
| **Admin-override** | All tables, for `platform_admins` role | Explicit additional policy granting read (and narrowly scoped write, e.g. `retailers.status`, `moderation_flags`) — audited via `audit_logs`, never a blanket bypass (System Architecture §5). |

`competition_insights` has no tenant column by design — it is populated only by a privileged backend process reading across tenants and writing pre-aggregated rows, so no retailer-facing RLS policy can accidentally expose another retailer's raw data (FR-COMP-002).

## 9. Indexing & Performance Notes

- `branches.geolocation` — GiST index for nearby-store queries (NFR-PERF-001, FR-DISC-001).
- `promotions (retailer_id, status, ends_at)` — composite index supporting the dominant "active promotions for retailer" and expiry-sweep queries.
- `products.embedding` — `ivfflat` (or `hnsw`) pgvector index for semantic search/recommendations (NFR-PERF-002).
- `engagement_events` — monthly range partitioning plus an index on `(retailer_id, occurred_at)` for dashboard queries (NFR-PERF-004); older partitions can be rolled up/archived per the data retention policy (NFR-PRIV-001).
- Full-text search index (`pg_trgm` or `tsvector`) on `products.name` / `promotions.raw_product_name` for FR-DISC-004 keyword search, bilingual (French/English) configs.
